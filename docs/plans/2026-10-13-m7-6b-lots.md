# M7.6b Batches in stock take, intake and merge (core) — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.
> Same shape as M7.6a. Opus executes and reviews, one commit per step, and UI gates are self-reviewed (4 combos, 1366 + 360).

**Goal:** batches (lots) can be added, counted and merged per product — on the Batches sheet, in stock-take and in
the count sheet — and stock intake tops up a matching batch instead of opening a new one every time.

**Architecture:** two new stock service calls carry every write: `AddStock` (top up a named lot or open a new one
with cost / price / expiry) and `MergeBatches` (fold lots into the oldest, no movement). Stock-take, the count
sheet, the Batches sheet and intake all route through them or the existing `Adjust{BatchID}`.

**Spec:** `docs/specs/2026-10-13-m7-6b-lots-design.md`. karots-pos source: its `batch-dual-pricing-design` note
(the stock-take "known limit" this closes); no karots-pos routes (suite-only).

## Global constraints

- Core never names a plugin; `make check-core` after every task. Plugin lists committed core-only.
- DTOs in `internal/api/dto_stock.go` → `make types`; never hand-edit `types.gen.ts`.
- `stock.quantity` = SUM(`stock_batches.qty_remaining`) before and after every write; stock value moves only by
  what an `adjust` movement records (a merge with an edited cost is audited, not a movement).
- UI says **batch**. Theme tokens only, admin works at 360px, 4 combos. Files ≤ 500 lines. No AI attribution.

## Review focus

1. A merge never changes `stock.quantity`, and with the default cost never changes stock value by more than the 2dp rounding — Task 2.
2. Emptied lots stay as rows at 0 and a return of a sale from one still restocks (`RestockLot` on a 0 lot) — Task 2.
3. An old count sheet (no `batch` column) imports exactly as before — Task 5.
4. Intake undo after some of the topped-up batch was sold does not fail — falls back to the oldest — Task 3.
5. Stock-take: a product whose batch counts are open never also applies its product-level count — Task 4.

### Task 1: `AddStock` (stock service)
- [ ] `internal/features/stock/add.go`: `AddStockInput{ProductID, BatchID int64; Qty, Cost, Price, Expiry, Note string}`;
  `(s *Service) AddStock(ctx, in, userID) (batchID int64, err error)` — one tx: qty > 0; `BatchID > 0` → lock the lot
  (`LockBatch`, product must match), `qty_remaining += qty, qty_received += qty`; else `InsertBatch` (cost blank → product
  cost, price blank → 0 = follows, expiry `YYYY-MM-DD` or NULL, source `adjust`); `Increment`; `adjust` movement valued at the lot cost.
- [ ] DB tests (`add_test.go`): new lot with cost/price/expiry; top-up raises both quantities; another product's lot → 404/validation;
  stock = SUM(lots). Commit `feat(stock): AddStock — top up a batch or open one with its own cost, price and expiry`

### Task 2: `MergeBatches` (stock service)
- [ ] `internal/features/stock/merge.go`: `MergeInput{ProductID int64; BatchIDs []int64; Cost, Expiry, Price string}`;
  `MergeDefaults(lots []Batch) (cost decimal, expiry *time.Time, price decimal)` (weighted cost 2dp, earliest expiry, oldest's price);
  `(s *Service) MergeBatches(ctx, in, userID) (keptID int64, err error)` — one tx, lock all `FOR UPDATE`; refuse < 2, foreign or
  empty lot; kept = oldest (`created_at`, id); kept `qty_remaining = sum`, `qty_received += others' remaining`, cost / expiry / price
  from the input (blank = the default); others `qty_remaining = 0`.
- [ ] DB tests: count unchanged, default cost value-equal (±0.01·qty), earliest expiry, edited values honoured, others at 0 and
  `RestockLot` still works on them, each refusal. Unit test for `MergeDefaults`. Commit `feat(stock): merge batches into the oldest`
